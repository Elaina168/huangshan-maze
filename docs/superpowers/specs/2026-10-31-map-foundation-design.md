# 第1阶段：地图与参数基础短设计

状态：阶段范围及顺序已获用户确认；用户已回复“开始做吧”，批准本具体方案实施。本轮保留当前冰岔迷宫的全部布局、物理参数、正常游玩的中文文案和操作，不提前实现选关、随机生成或机关。

## 目标与方案取舍

从现有常量几何迁移为板端可装载的数据，集中已有调节参数，提供加载边界上的合法性检查。后续关卡和板端随机生成可以复用相同数据入口，玩家不需要电脑工具。

推荐“通道字符串＋地面标记＋独立对象表”：奇数行/列的格心写`.`普通或`~`冰面，格间用`|`/`-`表示封闭、空格表示通道，`+`表示网格接点而非新增柱子。陷阱、起点、终点通过对象表给出精确圆心/半径。另一方案是把每个字符直接变成同尺寸实心墙块，但会改变现有8px薄墙和绕坑空间；本轮不采用。外部JSON解析器/文件系统也不需要引入。

最大7列×6行，每格50px，与现图一致；字符阵列为(2×行数+1)行、每行(2×列数+1)字符。本轮只扩展表示和装载，不把无限尺寸/任意机关组合纳入能力。

- 对象表仅实现本轮已有的起点、终点、陷阱；必须各有一个起点/终点。起终点位于格心，陷阱可在格内精确偏移；起点圆半径作为本关球半径。
- 板端装载结果提供已有maze_level_t几何视图，物理/app接口继续接收const视图；墙、材质和陷阱放在固定容量的加载结果中，不动态申请内存。装载结果由主入口静态持有，app/model/UI使用期间不覆写、不按值搬迁包含内部指针的结果；定义和稳定ID在使用期间有效。
- 旧maze_level_one和maze_level_surface_lab保留。当前冰岔不保留两套生产几何，旧坐标仅作为测试基线/已有设计证据。
- UI改用稳定ID判断当前图类型，不能依赖已不再固定的实例指针。屏幕标签和地图对象数量仍与0.6.1相同。

## 加载边界检查

1. 检查维度/行数/行长、位置对应字符、封闭外边界、容量及对象类型/数量；非法定义明确失败。
2. 生成墙和冰区，保持相邻墙端部4px延伸并裁剪至地图边界；按行扫描，先右边界再下边界，保持原墙顺序。外圈字符只用于封闭检查，不新增外圈实体墙，仍由model的球半径边界处理。
3. 检查圆心/半径有限且有效、地图范围、球半径安全起点、起终点格心、终点与陷阱/起点不重叠，以及陷阱本身不埋进墙内。地面格子不能同时含两种材质。
4. 用固定5px间隔的球心格点图做保守静态路线检查；每条横/纵边的球心都限制在[r,width-r]×[r,height-r]内，检查连续线段与墙的球半径间距，并按现有球心落坑规则避坑，终点使用实际圆区域。这样不会把两端安全但中间穿墙/穿坑的边当作可通行。
5. 最多71×61=4331格点，固定队列及位图工作区，预计约9.2KB，另有约数KB装载结果；以实际编译/sizeof为准。工作区固定为静态存储，只在装载期间使用，不放进8KB主线程栈或IMU栈，不在游玩帧循环反复检查。

此检查能提供离散安全路线见证，不是连续空间可达性的完备证明：窄到格点无法覆盖的合法路线可能被拒绝，错误说明为“未找到安全路线”，不能宣称数学上绝对无解。无控制输入的静态见证也不代替惯性轨迹验证；原两条真实model绕坑路线仍必须回归通过。新机关的状态可达性留到对应阶段扩展。
