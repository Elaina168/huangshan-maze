# 第一次本人修改：RGB 节奏与版本

状态：用户已完成源码修改，Codex 核对后构建通过；烧录与板端验证待执行。证据见 [本次构建记录](../../evidence/builds/2026-10-10-rgb-v0.1.1/README.md)。对应课程 C-06、C-18、C-21、C-24。该练习用于建立本人修改证明链，不代替迷宫产品用途和闭环验收。下文保留原操作步骤便于复现。

## 1. 为什么先做这一步

课程要求本人完成可观察修改、编译、烧录、验证，并解释入口和行为。由你实际编辑源码和操作板卡，Codex 协助检查差异、构建、记录和提交；如实记录辅助方式，不将 AI 修改写成本人独立修改。

本次只调整已有 RGB 例程：红、绿、蓝顺序不变，每色亮灯由 500 ms 改成 1000 ms，灭灯由 500 ms 改成 250 ms；版本由 0.1.0 改成 0.1.1。预期亮灯时间变长、灭灯时间变短，启动串口显示新版本。

## 2. 先由你编辑

打开仓库中的 `src/main.c`，不要编辑 `D:/sifli/peripheral_lab` 或临时构建副本。

确认现有内容：

```c
#define APP_VERSION     "0.1.0"
#define BLINK_ON_MS     500
#define BLINK_OFF_MS    500
```

把对应三行改为：

```c
#define APP_VERSION     "0.1.1"
#define BLINK_ON_MS     1000
#define BLINK_OFF_MS    250
```

同时更新文件开头的行为说明，把“亮 500ms、灭 500ms”改为“亮 1000ms、灭 250ms”。保存为现有 UTF-8、LF 换行。

理解修改路径：`main()` 遍历 `color_table`，设置颜色后调用 `rt_thread_mdelay(BLINK_ON_MS)`，灭灯后调用 `rt_thread_mdelay(BLINK_OFF_MS)`。参数单位是毫秒；这两个值是请求的等待时间，不能仅凭宏定义声称真机时间测量准确。

完成编辑后告知 Codex“改好了”。下一步检查 `git diff`，更新导入清单中的 modified 标记（保留原始来源 SHA-256），再构建，不绕过原样导入校验。

## 3. 构建与烧录顺序

1. Codex 核对源码差异、导入记录和材料检查，运行快照构建；失败则先修复，不下载旧产物。
2. 成功时检查退出码 0、三项固件和 `source_unchanged=true`，归档这次完整日志、状态与固件哈希。
3. 根据新 `build/build-state.json` 的 `stage_path` 打开它的 `project` 目录，在 CodeKit 使用 `sf32lb52-lchspi-ulp` 对应完整下载配置。实际串口以设备当前识别为准；历史 COM6 不能当作当前确认。
4. 由你操作烧录并保留完整输出。不要拿外设示例的配置下载到本次最小工程，也不要猜测单个 bin 的烧录地址。
5. 观察 RGB 和启动日志，记录实际结果，之后 Codex 将修改、构建证据与开发日志提交推送；上板结果不足时明确写未执行或待补，不宣称 C-06 已通过。

本次 RGB 工程没有迷宫界面，也不会保留外设测试台界面；验证对象是灯和串口。
