## 1. 这个版本做什么

在原RGB工程上启用I2C3，增加msh命令 `imu_probe`。main.c中的本人修改和亮灭时长保持原样，启动版本仍为v0.1.1；通过新命令和本次固件哈希区分诊断版本，不以相同启动版本推定刷对了固件。

每次命令取40点，样本之间等待50ms；器件加速度配置104Hz/±2g，这不是应用取样频率或显示帧率。输出单位raw（原始计数），无需浮点显示。只在msh线程取样，完成或失败后尝试恢复传感器配置。RGB日志穿插属于正常现象。

命令只接受neutral/right/left/up/down五个标签。这些是你声明的姿态，不是程序识别结果。`result=ok`只代表该次读取及配置恢复成功，不代表方向映射、稳定性或产品验收成功。

## 2. 烧录后先试一组

使用本次构建记录中的实际下载目录，先停止COM6监视，进入构建目录后运行uart_download.bat；不要使用上一轮RGB固件目录。端口以当前识别为准。

下载成功后再连接串口：1000000波特率、8N1、无硬件流控。msh默认关闭输入回显，看不见自己输入的文字不代表未接收。使用工具的文本发送框，末尾发送回车/换行。

固定屏幕朝向，在屏幕边框标记“上”，后续各组不旋转板子；记录该方向相对USB口的位置。本版没有绘制方向标记。先保持舒适中立姿态，输入：

```text
imu_probe neutral
```

采样前就保持姿态稳定，等待命令结束再移动。预期有begin、40条sample、range以及end行，例如最后一行字段形态为：

```text
[imu_probe] end pose=neutral result=ok count=40 mean_raw=<X>,<Y>,<Z>
```

尖括号是说明用占位符，不是已采数据。先将这一组完整日志发给Codex核对。若bus_missing、identity、sample_error、restore_error或命令找不到，保留原输出，停止继续采四向；不要把无效/不完整数据补成40点。

## 3. 再采四向

中立组成功后，每次先摆好姿态再发送命令，采样期间不动，前后沿用同一屏幕“上”的标记。

| 命令 | 实际操作 |
|---|---|
| `imu_probe right` | 右边缘压低，左边缘抬高 |
| `imu_probe left` | 左边缘压低，右边缘抬高 |
| `imu_probe up` | 上边缘压低，下边缘抬高 |
| `imu_probe down` | 下边缘压低，上边缘抬高 |
| `imu_probe neutral` | 最后回中立再采一次，观察前后基线变化 |

倾斜幅度保持适中、四向尽量相近；不移动屏幕接线或重新定义上边缘。保存完整日志与姿态说明；不用猜X/Y正负，也不套用自行车示例符号。

Codex对各组相对中立的均值变化、反向一致性、原始范围及两次中立差异作分析；证据不足时要求针对性重采，不预先写死映射。校准条件、死区、正式采样时效和运动参数需后续单独预研。

## 4. 限制

主机故障注入验证错误返回、签名解码与恢复逻辑，不验证I2C电气、真实RT-Thread调度或按姿态操作。就绪轮询设200ms截止，底层驱动I2C默认5000ms超时，不能把200ms解释成整个命令故障响应上限。诊断等待期间msh处理该命令，RGB线程继续工作；这不是未来UI架构。
